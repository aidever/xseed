约定：
- `‖` 表示字节串拼接；`u16be`、`u32be`、`u64be` 表示大端定长整数。
- `H` = SHA-256；`HKDF(ikm, info, L)` = HKDF-SHA256（salt 为空）；`HMAC` = HMAC-SHA256。
- 所有域分隔标签使用 ASCII 字面量，形如 `"xseed/…/v1"`。
- 文中“实现时核实”表示依赖第三方行为、必须在实现阶段实测确认的细节。
- 角色：**持有者**（被查询、出题、告知的一方，下文记为 A）、**查询方**（查询、答题、加种的一方，记为 B）。每台设备同时扮演两种角色。

## 1. 模块详细设计

### 1.1 指纹

#### 1.1.1 文件列表规范化

输入为种子的 info 字典（v1、v2 或混合）。

```
fn normalized_entries(info) -> Vec<(Bytes, u64)>, root_name:
    root_name = NFC(info.name)
    if v1 单文件（info.length 存在）:
        return [(NFC(info.name), info.length)], root_name      # 单文件：文件名参与（FR-XSP-002）
    files = v1: info.files；v2-only: 深度优先遍历 info["file tree"]，按字节序遍历键
    out = []
    for f in files（保持种子中的顺序）:
        if f.attr 含 'p' 或 path[0] == ".pad": continue        # BEP 47 填充文件
        p = 用 "/" 连接 [NFC(c) for c in f.path]                # 不含根目录名
        if p 为空、含 "." 或 ".." 组件、含 NUL、以 "/" 开头: return Err(InvalidPath)
        out.push((utf8(p), f.length))
    if out 为空: return Err(Empty)
    return out, root_name
```

- 路径组件必须是合法 UTF-8；存在 `path.utf-8` 时优先使用；都不合法时视为无效种子，不参与辅种。
- 大小写不做折叠；路径分隔符统一为 `/`。

#### 1.1.2 结构指纹、位置键与桶

```
SFP    = H( "xseed/sfp/v1" ‖ 0x00 ‖ u32be(n) ‖
            for (p, len) in entries: u32be(|p|) ‖ p ‖ u64be(len) )
L      = H("xseed/loc/v1" ‖ SFP)
bucket = u16be(L[0..2])              # 0..65535
```

两个种子的 `SFP` 相同，即满足辅种判定（FR-XSP-002）。

### 1.2 本地清单（inventory）

```
loop every 10 min or on downloader event:
    for t in downloader.list_completed():                  # 进度 == 1.0
        if t.state ∉ 做种类状态: skip
        if known(t.info_hash) and t.unchanged: continue
        info = downloader.torrent_info(t)                  # §1.10：优先导出原始种子；不支持时用文件列表
        (entries, root) = normalized_entries(info) else mark invalid
        site = sites.identify(downloader.trackers(t))      # §1.11
        tid  = resolve_torrent_id(t, site)                 # §1.2.1
        upsert local_torrents(sfp, bucket, site_ref, torrent_id = tid, save_path, root_name, …)
```

指纹只来自种子元数据，不读取数据文件（NFR-XSP-004）。

#### 1.2.1 本机种子编号解析

持有者要告知种子编号，必须先知道本机种子在该站的编号。按顺序尝试：

1. 种子的 `comment` 或 `source` 字段（qB `torrents/properties.comment`、TR `comment`）中，属于该站域名的 URL，按站点定义的 `details_pattern` 提取编号；默认规则依次匹配查询参数 `id`、`torrentid`、`tid`，以及路径 `/torrents/<数字>`；
2. 用户在 PT-depiler 备份中勾选了“下载历史”时，按 info_hash 或种子名匹配下载记录中的站点与编号（实现时核实 PT-depiler 下载历史的字段）；
3. 都失败时 `torrent_id = NULL`：该种子不作为持有者登记，只作为查询方使用。

### 1.3 节点选择与 HRW

```
fn owners(bucket, nodes, R=2) -> [node]:
    for n in nodes:
        u = (u64be(H("xseed/hrw/v1" ‖ n.id ‖ u16be(bucket))[0..8]) + 0.5) / 2^64   # (0,1)
        score[n] = -ln(u) / n.effective_weight
    return 取 score 最小的 min(R, |nodes|) 个
effective_weight = manifest.weight × ramp(age)        # ramp：上线 14 天内从 0.1 线性升到 1.0
```

入口节点的选择：取最近 3 次 RTT 中位数最小的节点；连续 3 次失败后降级 1 小时并自动切换。用户可以在设置中固定入口节点。

### 1.4 代号、两跳登记与查询

#### 1.4.1 代号

代号是入口节点签发的 16 字节不透明值，用来把消息路由到某个信箱，同时不暴露信箱身份：

```
plain  = u32be(slot) ‖ u16be(gen) ‖ u16be(week) ‖ rand(4) ‖ 0x00000000
alias  = AES-128-Enc(K_alias, plain)            # 单分组，K_alias 是入口节点私有密钥
```

- `slot`：信箱在入口节点上的槽位号；`gen`：槽位被回收重用时递增，防止投错；`week`：签发时的 ISO 周序号，超过 3 周的代号拒收。
- 入口节点解析时解密并检查末 4 字节为 0，伪造成功率 2⁻³²；不需要保存代号表。
- 节点标识：索引中用 `node_tag = node_id[0..4]` 表示代号所在的入口节点，注册中心保证 `node_tag` 唯一。
- agent 为**每个本机种子**分配一个代号（同一内容在两个站各有一个种子，就是两个代号）；每周用新代号重新登记。查询方每次会话也使用一个新代号作为回信地址。

#### 1.4.2 两跳封装

- HPKE（RFC 9180）：`DHKEM(X25519, HKDF-SHA256)`、`HKDF-SHA256`、`ChaCha20Poly1305`，Base 模式，`info = "xseed/ohttp/v1" ‖ target_node_id`。
- 请求：`enc ‖ ct`；响应：用 HPKE 导出密钥 `export("xseed/ohttp/resp", 32)` 加 `ChaCha20Poly1305`（随机 12 字节 nonce 置于密文前）。
- 明文按 512 字节的倍数填充，减少长度泄露。入口节点只看到目标节点 ID 与密文长度。
- 目标桶节点恰好是自己的入口节点时，改经 RTT 次低的另一个节点转发。

#### 1.4.3 操作

| 操作 | 明文（CBOR） | 说明 |
|---|---|---|
| `REGISTER` | `{op:1, entries:[{b:u16, node:u32, alias:bytes16}] ≤ 64, ttl_d:u8 ≤ 3, pow:Pow}` | 同一桶内相同 `alias` 视为刷新；不提供注销，停止刷新即在 TTL 后过期 |
| `LOOKUP` | `{op:2, buckets:[u16] ≤ 16}` | 返回 `{b: [{node, alias}]}`，每个桶最多 128 条，超出时随机抽样 |

登记发送策略：每天把全部（桶，代号）按 HRW 分组，每批 ≤ 64 条、桶号打乱，分散在全天随机时刻发送，使桶节点难以把同一批条目归为同一设备。

工作量证明 `Pow = {salt:bytes16, nonce:u64}`：`H("xseed/pow/v1" ‖ server_salt ‖ salt ‖ u64be(nonce))` 至少有 `bits` 个前导零比特；`REGISTER` 默认 16 位，`/v1/mailbox` 默认 20 位；`server_salt` 来自目标节点 `/.well-known/xseed`，每小时轮换。

### 1.5 会话与加密

#### 1.5.1 探测

```
K_probe = HKDF(SFP, "xseed/probe/v1", 32)
nonce   = random(16)
tag     = HMAC(K_probe, nonce ‖ to.alias ‖ from.alias)[0..16]
PROBE   = {t:"probe", v:2, nonce, tag, sid:random(16)}
```

持有者按 `to.alias` 找到对应的本机种子（一个代号只对应一个种子），用其 SFP 校验 tag（常量时间比较）；匹配就回 `PROBE_ACK{sid}`，否则不回应。

#### 1.5.2 Noise 握手

- 模式：`Noise_XXpsk3_25519_ChaChaPoly_BLAKE2s`（`snow`）；查询方为发起方。
- `psk = HKDF(SFP, "xseed/psk/v1", 32)`；prologue = `"xseed/v2" ‖ sid`。
- 静态密钥每个会话重新生成，会话之间不可关联。
- 握手完成后取握手 hash `h`，派生 `K_cb = HKDF(h, "xseed/cb/v1", 32)`，作为答题的绑定密钥。
- 应用层分帧：`u16be(len) ‖ cbor`，单条 ≤ 4 KiB；每条消息填充到 256 字节的倍数。

#### 1.5.3 会话状态机

```
Init ─PROBE→ Probing ─ACK→ Handshaking ─3 条消息→ Asking
Asking ─ASK{site}→ 持有者判定：
    NOT_MEMBER                          → Closed(not_member)
    CHAL{torrent_id}                    → Answering ─ANSWER{mac}→
        错误                            → Closed(bad_answer)
        正确 且 代号对应种子 ∈ site      → OFFER → Done
        正确 且 代号对应种子 ∉ site      → NONE  → Done
任一状态：超时、解码失败、收到 ERROR → Closed(reason)
```

| 阶段 | 超时 |
|---|---|
| Probing | 15 s |
| Handshaking | 20 s |
| Asking | 10 s |
| Answering | 120 s（含查询方下载题目种子） |
| 整个会话 | 240 s |

一次会话只询问一个站点。查询方需要询问多个站点时，每个站点单独开会话，各自使用新的回信代号，会话之间随机间隔 1–30 min。

### 1.6 会员验证（答题）

#### 1.6.1 持有者的判定

```
on ASK{site}:
    pool = challenge_pool.pick(site)          # 本机该站题库中随机一题，排除 uses ≥ 50 或超过 30 天的
    if pool 为空: reply NOT_MEMBER             # 本机不是该站会员，或题库暂不可用
    else: reply CHAL{torrent_id: pool.torrent_id}；记录 expected = pool.ih
on ANSWER{mac}:
    ok = ct_eq(mac, HMAC(K_cb, "xseed/ans/v1" ‖ site_bytes ‖ torrent_id ‖ expected))
    if !ok: reply ERROR(21) 并关闭；peer 计入失败
    t = 代号对应的本机种子
    if t.site == site and t.torrent_id 非空: reply OFFER{torrent_id, ih1?, ih2?, size}
    else: reply NONE
```

“是会员但没有”与“是会员且有”都先出题，答对之后才区分，询问本身不泄露资源是否在该站。

#### 1.6.2 题库（持有者）

```
refill(site):                                   # 每站每周最多 4 次，每次最多下载 4 个
    M = max(本机该站种子编号, answer_cache 中该站编号, offers 中该站编号)   # 仅限数字编号
    if M 不存在: return                          # 非数字编号的站点不出题，等价于不作为持有者
    repeat 至多 12 次 直到新增 4 题:
        id = uniform(max(1, M − 5000), M)
        if id ∈ 本机该站种子编号: continue        # 题目与本机无关
        bytes = sites.download(site, id) else continue     # 404、无权限、限流都跳过
        ih = info_hash(bytes)
        insert challenge_pool(site, id, ih)
保持每站 8–16 题；单题最多使用 50 次，超过 30 天淘汰
```

#### 1.6.3 答题（查询方）

```
on CHAL{torrent_id}:
    ih = answer_cache.get(site, torrent_id)
    if ih 为空:
        if 今日该站答题下载数 ≥ daily_answer_limit: send ERROR(40)；return
        bytes = sites.download(site, torrent_id) else send ERROR(22)；return
        ih = info_hash(bytes)；answer_cache.put(site, torrent_id, ih)
    send ANSWER{mac: HMAC(K_cb, "xseed/ans/v1" ‖ site_bytes ‖ torrent_id ‖ ih)}
```

`ih` 取 v1 info_hash（20 字节）；纯 v2 种子取 v2 info_hash（32 字节）。`site_bytes` 为 `SiteRef` 的确定性 CBOR 编码。各持有者都从站点近期编号中出题，查询方的答题缓存命中率随使用增加。

#### 1.6.4 通道绑定的安全性论证

设中间人 M 与持有者 A 建立会话（握手 hash 为 h₁），同时诱使某个真会员 C 与自己建立会话（h₂），把 A 的题目转给 C 作答。C 的答案为 `HMAC(HKDF(h₂), …)`，在 h₁ 下校验必然失败。M 要产生在 h₁ 下有效的答案，就必须自己知道题目种子的 info_hash，也就是自己能从该站下载种子，即 M 本身是会员。结论：任何人只能以自己的真实会员身份通过验证（FR-XSP-006）。

另外，M 要完成与 A 的握手必须知道 SFP（psk 由其派生），即 M 本身持有该种子；不持有的人连题目都看不到。

#### 1.6.5 防关联与残余风险

| 威胁 | 设计 |
|---|---|
| 查询方把同一持有者的多次回答关联起来，用站点同伴列表求交集定位用户名 | 每个本机种子一个代号，每周轮换；会话静态密钥每次重新生成；题目与本机无关 |
| 查询方一次问多个站，得知同一人在多个站的身份 | 一次会话只问一个站；同一内容在不同站的本机种子使用不同代号 |
| 持有者把同一查询方的多次询问关联起来 | 查询方每次会话使用新的回信代号；会话间隔随机 |

| 残余风险 | 说明 | 结论 |
|---|---|---|
| R1 会员身份 | 持有同一内容的人，可以通过 `NOT_MEMBER` 与 `CHAL` 的差别得知“某个匿名持有者是不是某站会员” | 只关联到匿名代号，不涉及资源与编号；接受 |
| R2 入口节点 + 桶节点合谋 | 两者合谋可以把 IP 与桶号关联（仍不知道站点与编号） | 节点由不同运营者提供；用户可固定可信入口节点；接受 |
| R3 同一入口节点 | 同一持有者的所有代号都在同一入口节点，`node_tag` 相同 | 入口节点同时服务大量用户，只能缩小到“该节点用户”；接受 |
| R4 真会员枚举 | 真实会员可以从其他会员处得到该站种子编号 | 他本来就能在站内搜到，这正是辅种的目的；不属于风险 |

### 1.7 信封与转发

信箱 WebSocket 上的每一帧都是一个 CBOR 信封：

```
Addr     = {node: u32, alias: bytes16}
Envelope = {v:2, to: Addr, from: Addr, sid: bytes16,
            kind: "probe" | "probe_ack" | "noise" | "close", body: bytes}
```

- agent 发出信封时，入口节点解密 `from.alias`，确认其槽位就是发送方的信箱，防止伪造回信地址。
- 目标 `to.node` 是自己时直接投递；否则以 `/v1/fwd` 转给目标入口节点，请求体为 `{env, origin: node_id, ts, sig: Ed25519(origin_sk, "xseed/fwd/v1" ‖ H(cbor(env)) ‖ u64be(ts))}`。接收节点用注册中心中 origin 的公钥验签，时间差超过 60 s 就拒收。
- 目标信箱不在线时返回 `404 xseed.node.mailbox_offline`，不暂存；查询方稍后重试（最多 3 次，间隔 1 h、6 h、24 h）。
- 节点不接受、也不转发任何直连地址；对端之间永远只通过节点通信（FR-XSP-007）。

### 1.8 取种（查询方）

```
on OFFER{torrent_id, ih1?, ih2?, size}:
    insert offers(...)；create job
job:
    if 今日该站加种数 ≥ daily_add_limit: 延到次日
    bytes = sites.download(site, torrent_id) else fail(no_source / site_*)
    t = parse(bytes)
    require info_hash(t) == offer.ih           else fail(ih_mismatch)；对端计入失败
    require SFP(t) == local.sfp                else fail(sfp_mismatch)；对端计入失败
    require announce 主机 ∈ site.tracker_hosts（或 Host 身份下等于该 host）else fail(foreign_tracker)
    require downloader 中不存在该 info_hash    else done(already_present)
    → §1.10 加入
```

下载到的种子带查询方自己的 passkey，直接使用，不做任何改写。

### 1.9 核对与可选抽查

默认不读数据文件：SFP 一致即认定内容一致，跳过校验（FR-XSP-009）。

加入前再检查一次原种子：进度 == 1.0，状态属于做种类，保存位置未变化。

配置了 `data_path_map`（小助手能访问数据目录）且开启 `sample.enabled` 时，额外抽查：

```
sample(t, local):
    pieces = ∅
    for each file f in entries(t): pieces += piece_index(f.start) ∪ piece_index(f.end - 1)
    pieces += 2 个随机 piece
    截断到 sample.max_pieces（优先保留小文件的首尾 piece）
    for p in pieces: SHA1(read(local, piece_range(t, p))) == t.pieces[p] else return Mismatch
```

站点标记 `allow_skip_check: false` 时不跳过校验，由下载器自行校验。

### 1.10 下载器适配与安全规则

```rust
#[async_trait]
pub trait Downloader {
    async fn list_completed(&self) -> Result<Vec<LocalTorrent>>;      // info_hash、名称、save_path、状态、分类
    async fn torrent_info(&self, t: &LocalTorrent) -> Result<TorrentInfo>; // 原始 info 或文件列表
    async fn properties(&self, ih: &InfoHash) -> Result<Props>;      // comment、save_path
    async fn trackers(&self, ih: &InfoHash) -> Result<Vec<TrackerEntry>>;
    async fn add(&self, req: AddRequest) -> Result<()>;
    async fn status(&self, ih: &InfoHash) -> Result<Option<TorrentStatus>>;
    async fn start(&self, ih: &InfoHash) -> Result<()>;
    async fn remove_keep_data(&self, ih: &InfoHash) -> Result<()>;   // 没有任何删除数据的接口
}
pub struct AddRequest {
    torrent: Vec<u8>, save_path: String, layout: Layout,   // Original | NoSubfolder
    rename_root: Option<String>, skip_check: bool, category: Option<String>, tags: Vec<String>,
}
```

`torrent_info`：qB 优先 `torrents/export` 取原始种子；不支持时用 `torrents/files`，此时多文件种子若以“无子文件夹”布局加入，无法区分单文件与多文件，标记为 `invalid(layout_unknown)`。TR 使用 `torrent-get` 的 `files`。

**布局：**

| 情况 | qBittorrent | Transmission |
|---|---|---|
| 单文件，或根目录名相同 | `savepath = 原 save_path`，`contentLayout=Original` | `download-dir = 原 downloadDir` |
| 多文件，根目录名不同 | `savepath = 原 save_path/原根目录名`，`contentLayout=NoSubfolder`，新种子的文件直接落在原根目录下 | `download-dir = 原 downloadDir`，加入后 `torrent-rename-path` 把新根目录名改为原根目录名（实现时核实：目标路径已存在、源路径不存在时 TR 是否只改元数据） |

小助手全程不访问数据目录，路径只在下载器内部解释，因此不存在容器路径映射问题。

| 规则 | qBittorrent | Transmission |
|---|---|---|
| 停止状态加入 | `stopped=true`（5.x）/ `paused=true`（4.x） | `paused=true` |
| 跳过校验 | `skip_checking=true`（站点不允许时为 false） | 无对应参数（实现时核实加入时是否自动校验） |
| 不自动管理 | `autoTMM=false`；`category` 沿用原种子 | — |
| 标记 | `tags=xseed` | `labels=["xseed"]`（TR ≥ 4.0） |
| 移除 | `torrents/delete`，`deleteFiles=false` | `torrent-remove`，`delete-local-data=false` |
| 只操作自己加入的 | 移除、启动前检查 `added_torrents` 中有记录**并且**带 `xseed` 标签 | 同左 |
| 幂等 | 加入前检查 info_hash 是否已存在 | 同左 |

加入后流程：启动 → 30 s 后检查状态，`missingFiles` / `error` → `remove_keep_data`，原因 `missing_files` → 观察首次 announce，`unregistered` 或认证失败 → 移除，原因 `tracker_*`。`remove_keep_data` 在实现层面硬编码 `deleteFiles=false`，并有单元测试断言请求参数。

### 1.11 站点识别

#### 1.11.1 主机规范化

`TrackerHost = lowercase(IDNA-ASCII(host)) ‖ (":" ‖ port，若不是 scheme 的默认端口)`。只保留 http、https、udp 三种 scheme。

#### 1.11.2 匹配

```
fn identify(trackers) -> SiteRef | Ambiguous | None:
    hosts = {normalize(t.url) for t in trackers} − public_trackers   # 注册中心提供公共 tracker 列表
    sites = {s | ∃ h ∈ hosts: h ∈ s.tracker_hosts or h 以 "." ‖ d 结尾（d ∈ s.domains）}
    if |sites| == 1: return Site(s.id)
    if |sites| > 1: return Ambiguous           # 不登记、不查询
    if |hosts| ≥ 1: return Host(min(hosts))    # 无站点定义：以 tracker 主机为身份
    return None
```

`SiteRef = {kind:"site", id} | {kind:"host", host}`。`Host` 身份下，持有者判定“种子 ∈ site”的条件是种子的 tracker 主机集合包含该 host。

#### 1.11.3 下载地址

依次尝试（成功的模板写入 `site_traits.download`）：

1. 站点定义的 `download_template`（导入 PT-depiler 时按框架生成）；
2. 无站点定义时按通用模板：NexusPHP `https://{domain}/download.php?id={id}&passkey={passkey}`，以及带 Cookie 的 `https://{domain}/download.php?id={id}`；
3. 都失败就放弃，Web UI 提示为该站同步或填写 Cookie。

带凭证的请求只发往该站已知域名（站点定义的 `domains`，或 Host 身份下与 tracker 同一可注册域名）；跨域重定向不携带凭证。按站限速默认 2 次/分钟。

### 1.12 站点凭证

#### 1.12.1 来源与优先级

| 来源 | 内容 | 优先级 |
|---|---|---|
| PT-depiler（WebDAV） | 站点 Cookie；站点列表与域名映射 | 1 |
| tracker 地址 | 本机该站种子 announce 地址中的 `passkey`、`authkey`、`torrent_pass` 参数，或路径中 32 位十六进制段 | 2 |
| 手动 | 用户在站点页填写的 Cookie / passkey | 3（用户显式填写时覆盖自动来源） |

#### 1.12.2 PT-depiler WebDAV 接收端

只实现 PT-depiler 实际使用的子集（基于其 `webdav` 客户端：列目录、上传、下载、删除）：

| 方法 | 路径 | 行为 |
|---|---|---|
| `OPTIONS` | `/ptd/` | `DAV: 1` |
| `PROPFIND` | `/ptd/`（Depth 0 / 1） | 返回空目录（不保留备份文件） |
| `PUT` | `/ptd/PTD_backup_<yyyyMMddTHHmm>.zip` | 接收并解析，返回 201；其他文件名返回 403 |
| `GET` / `DELETE` | `/ptd/*` | 404 / 204 |

- 鉴权：HTTP Basic，独立于 Web UI 的随机用户名和 24 位随机密码；连续 10 次失败封禁来源 IP 1 小时。PT-depiler 中不要勾选 Digest。
- 限制：上传 ≤ 64 MiB；只解压 `manifest.json`、`cookies.json`、`metadata.json`，单个解压后 ≤ 32 MiB，总解压 ≤ 64 MiB。
- 格式（M1 实现时按 PT-depiler 源码核实）：`manifest.json` 为 `{ time, version: "PT-Depiler (<版本>)", encryption: bool, files: Record<键, { name, hash }> }`，`files` 是以 `cookies`、`metadata` 等为键的**对象**，`name` 为 `<键>.json`。
- 校验：`files[键].hash` 为对应 zip 内文件内容（加密时即密文字符串）的 MD5 十六进制，不一致即拒绝。
- 解密：`encryption == true` 时，每个 json 文件内容为 crypto-js 口令格式的 AES 密文（Base64；`Salted__` + 8 字节 salt，EVP_BytesToKey（MD5）派生 AES-256-CBC 密钥与 IV；没有 `Salted__` 前缀时 salt 为空）。**口令不是用户填写的密钥本身**，而是 `md5Hex(密钥)` 的前 16 个字符（PT-depiler `aesEncryptOpenSsl(json, md5(key).substring(0, 16))`）。
- 提取：`cookies.json` → `Record<host, chrome.cookies.Cookie[]>`，按 `name=value; …` 拼成 Cookie 头；`metadata.json` → `sites`（`Record<站点键, 站点配置>`，显示名取 `merge.name`，缺省用站点键）与 `siteHostMap`（`Record<域名, 站点键>`）。其余字段不读取。
- 站点定义：每个站点键写入 `site_defs`（`source = ptd`，`domains` 为 `siteHostMap` 中指向它的全部域名），之后对下载器做一次全量重扫，原来按 tracker 主机识别为 `host:<主机>` 的种子会归到 `site:<站点键>`。
- 存储：Cookie 按站点加密写入 `credentials`（来源 `ptd`），覆盖上一次同步的值；原始 zip 解析后立即丢弃。
- 兼容：`manifest.version` 不以 `PT-Depiler (` 开头或解析失败时，界面提示“PT-depiler 备份格式无法识别”，保留上一次的凭证，不影响辅种。

## 2. 接口详细设计

### 2.1 节点 HTTP 接口

#### `GET /.well-known/xseed`

```json
{"proto":[2],"node_id":"3f2a…","load":0.42,"time":1794000000,
 "pow_salt":"…","challenge_sig":"…"}
```

`?challenge=<hex32>` 时，`challenge_sig = Ed25519(sign_sk, "xseed/wk/v1" ‖ challenge)`，供 CI 验证节点确实持有清单中的密钥。

#### `POST /v1/mailbox`

请求：`{pow}`（20 位）。响应：`{slot_token: bytes16, secret: bytes32}`。节点只保存 `H(secret)`。限流：每个 IP 每天 10 个。

#### `GET /v1/mailbox/ws`

鉴权：连接建立后服务端发送 `{challenge: bytes32}`，客户端回复 `{slot_token, mac: HMAC(secret, "xseed/ws/v1" ‖ challenge)}`。之后双方收发 Envelope（§1.7）。心跳每 30 s；90 s 无响应断开。同一信箱只允许 1 条连接。

#### `POST /v1/aliases`

请求头：`Authorization: XSeed slot=<hex>, ts=<unix>, mac=<HMAC(secret, "xseed/alias/v1" ‖ ts ‖ n)>`；请求体 `{n: u16 ≤ 4096}`。响应：`{aliases: [bytes16]}`。每个信箱每天最多 20000 个。

#### `POST /v1/ohttp`

请求：`{target: node_id, req: bytes ≤ 16 KiB}`，需信箱鉴权（同上）。入口节点以 `/v1/gateway` 转发给目标节点，原样返回响应字节，不解析 `req`。

#### `POST /v1/gateway`

请求：`{req}`，来源必须是注册中心中的节点（mTLS 或请求签名，同 `/v1/fwd`）。解封装后执行 §1.4.3 的操作，返回封装后的响应。

#### `POST /v1/fwd`

请求：§1.7 中的签名结构。目标信箱不在线返回 `404 xseed.node.mailbox_offline`。

#### 限流与配额（默认值）

| 对象 | 限制 |
|---|---|
| 每个信箱的 `/v1/ohttp` | 600 次/小时 |
| 每个信箱发出的探测 | 60 次/分钟 |
| 每个代号收到的探测 | 30 次/小时，超出丢弃 |
| 每个信箱收到的信封 | 600 条/分钟 |
| 每个会话经节点的流量 | 16 KiB |
| 每个来源节点的 `/v1/fwd`、`/v1/gateway` | 2000 次/秒 |

### 3.2 node 内存结构

```rust
struct Mailboxes { slots: Vec<Slot> }                  // 按 slot 号索引
struct Slot { gen: u16, secret_hash: [u8; 32], conn: Option<Sender>, last_seen: u32 }
struct Entry { alias: [u8; 16], node: u32, exp_day: u16, _pad: u16 }   // 24 字节
struct Index { buckets: Box<[RwLock<Vec<Entry>>; 65536]> }            // 每桶上限 8192 条，超出淘汰最早过期的
```

内存估算：每条登记 24 字节，加 `Vec` 容量冗余按 1.3 倍计约 31 字节。1500 万条约 470 MiB；1 万条长连接约 100 MiB；合计约 600 MiB，满足 1c1g（NFR-XSP-001）。

整体规模：1 万台设备 × 每台 3000 个种子 × R=2 = 6000 万条，需要 4 个 1c1g 节点；节点越多，每个节点承担越少。

快照：收到 SIGTERM 时把 `Index` 与 `Mailboxes`（不含连接）写成 bincode 文件，启动时载入。

## 6. 安全设计

### 6.1 威胁与对策

| 威胁 | 等级 | 对策 |
|---|---|---|
| 恶意节点收集“IP ↔ 指纹” | 高 | 两跳登记与查询（§1.4.2）；入口节点看不到指纹，桶节点看不到 IP |
| 批量刷出站点资源目录 | 高 | 答题（§1.6）；没有站点账号答不出题，拿不到任何编号 |
| 用同伴列表求交集定位持有者 | 高 | 每种子一个代号、每周轮换；题目与本机无关（§1.6.5） |
| 跨站关联身份 | 高 | 一次会话只问一个站；不同站的种子用不同代号 |
| 本机凭证被窃取（恶意网页、DNS 重绑定） | 高 | Web UI 必须登录；Host / Origin 校验；CSRF token；凭证加密存储；日志脱敏 |
| 种子路径穿越 | 高 | §1.1.1 拒绝 `..`、绝对路径、NUL；小助手不写数据目录，路径只交给下载器 |
| 刷垃圾登记、打爆节点 | 中 | 工作量证明；按信箱、代号、来源节点限流 |
| 投毒（告知错误编号） | 中 | 下载后核对 info_hash、结构指纹与 tracker 主机，不一致即丢弃 |
| 借刀下载（反复出题让对方账号狂下种子） | 中 | 答题缓存；每站每天答题下载上限；每代号探测上限 |
| 站点模板被篡改以窃取 Cookie | 中 | 注册中心签名；带凭证请求只发往站点已知域名；跨域重定向不带凭证 |
| 恶意 zip（PT-depiler 接收端） | 中 | 大小与解压上限；只解压 manifest 列出的三个文件；MD5 校验 |
| WebDAV 被暴力破解 | 中 | 24 位随机密码；失败封禁；建议 PT-depiler 加密备份 |
| 知道指纹的节点做中间人 | 低 | 通道绑定使代答无效（§1.6.4）；他最多看到自己本来就持有的内容的对话 |
| 注册中心被篡改 | 低 | 所有者离线签名；主备公钥轮换 |
| 软件更新供应链 | 低 | 可复现构建；发布物 minisign 签名；不静默自动更新 |

### 6.2 实现约束

| 项 | 措施 |
|---|---|
| 密码学原语 | X25519、ChaCha20-Poly1305、BLAKE2s（Noise）；SHA-256、HKDF、HMAC；AES-128（代号）；Ed25519；HPKE（RFC 9180）；均使用经过审计的 crate |
| 常量时间比较 | 所有 MAC、tag 比较使用 `subtle` |
| 输入校验 | bencode：嵌套深度 ≤ 32、单个种子 ≤ 16 MiB、文件数 ≤ 100000；CBOR：单条 ≤ 16 KiB、数组 ≤ 4096 |
| 下载器 | 只有 `remove_keep_data`，没有删除数据的代码路径；操作前检查 `added_torrents` 与标签 |
| 日志 | URL 查询参数整体替换为 `?…`；32 位以上十六进制串与 Cookie 值打码；不记录种子编号与站点组合 |
| 节点 | 不记录信封内容；访问日志默认不记 IP |

## 7. 性能设计

### 7.1 节点容量

| 资源 | 估算（单节点） |
|---|---|
| 长连接 | 1 万条 × 约 10 KiB = 100 MiB |
| 桶登记 | 1500 万条 × 约 31 字节 ≈ 470 MiB（§3.2） |
| CPU | 登记刷新：全网 6000 万条 / 天，每批 64 条，约 11 次 HPKE 解封装 / 秒（每次约 50 µs）；探测与转发每秒数百条 |
| 重连风暴 | 客户端 0–120 s 随机延迟重连；TLS 握手单核约 1000 次 / 秒 |

### 7.2 流量

| 项 | 单次 | 1 万台设备 / 天（每台 20 个新种子，每个探测 5 个持有者） |
|---|---|---|
| 查询（两跳） | 约 1 KiB × 2 节点 | 约 0.4 GiB |
| 会话（探测、握手、询问、答题、告知） | 约 3 KiB × 2 个入口节点 | 约 6 GiB，分摊到所有节点 |
| 种子文件 | 0（查询方直接从站点下载） | — |

### 7.3 agent

- 读盘：默认 0；开启抽查时每个任务 ≤ 32 个 piece。
- 站点请求：每个新辅种 1 次种子下载，加上 ≤ 1 次答题下载（命中缓存时为 0）；题库每站每周 ≤ 16 次下载。
- 并发：每个站点 1 个下载并发；会话并发 ≤ 8。
