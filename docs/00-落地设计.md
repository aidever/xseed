## 1. 范围

**v1 要做：**

- 辅种小助手 `xseed-agent`；
- 社区节点 `xseed-node`：一个 Rust 二进制，同时具备牵线、信令、中继功能；
- Cloudflare 节点：用 workers-rs 包装同一套核心代码，作为官方免费节点；
- 注册中心 `xseed-registry`：一个 GitHub 仓库，存放节点列表和站点定义库，内容签名后发布；
- 站点侧：`crossseed-api` 新增会员钥匙接口和策略声明。

**v1 不做：** 部分辅种、跨文件系统复制数据、Deluge / rTorrent 适配、捐赠。

## 2. 组件

```
                 ┌──────────── 注册中心（GitHub 仓库 xseed-registry）────────────┐
                 │ nodes/*.yaml 节点清单   sites/*.yaml 站点定义   CI 健康检查   │
                 │ → 签名的 index.json，发布到 Releases / Pages / jsDelivr       │
                 └──────────────────────────┬──────────────────────────────────┘
                                            │ 每 6 小时拉取一次，验证签名
        ┌───────────────────────────────────┼───────────────────────────────────┐
        ▼                                   ▼                                   ▼
  xseed-node A（社区 1c1g）          xseed-node B（Cloudflare）          xseed-node C（社区）…
  信箱 · 桶索引 · 中继               信箱 · 桶索引 · 中继               各节点之间互不通信
        ▲                                   ▲                                   ▲
        └────────────── 小助手按同一份节点列表算出“哪个桶归哪个节点” ─────────────┘
```

| 组件 | 形态 | 状态 |
|---|---|---|
| `xseed-agent` | Rust 单文件二进制 + Docker 镜像（amd64 / arm64），内置 Web UI | 本地 SQLite，凭证加密存储 |
| `xseed-node` | Rust 单文件二进制（tokio + rustls），可以选择开启哪些角色：信箱 / 桶索引 / 中继 | **只在内存中保存软状态**，重启后由小助手重新登记，不需要数据库 |
| Cloudflare 节点 | workers-rs 包装的同一个核心 crate（`xseed-core`），运行在 Worker + Durable Objects 上 | 同上 |
| `xseed-registry` | GitHub 仓库 + CI | 节点清单、站点定义库 |
| 站点侧 | `crossseed-api` 新增 `GET /v1/group-key`、`/.well-known/pt-xseed` | 会员钥匙每周轮换 |

协议逻辑（桶归属计算、消息校验、限流规则）全部放在 `xseed-core` 中，Rust 原生节点和 Cloudflare 节点只是两种外壳，避免维护两套实现。

## 3. 容量与费用

### 3.1 一台 1c1g 服务器能承载多少

假设：每台设备 3000 个种子，每天新增 20 个；桶前缀 16 位（共 65536 个桶）。以下是估算，上线前要用压测确认。

| 资源 | 1 万台在线设备时的用量 | 说明 |
|---|---|---|
| 内存：信箱长连接 | 约 100 MB | 每条 WebSocket 连接约 10 KB（收发缓冲区调小） |
| 内存：桶索引 | 约 200 MB | 1 万 × 3000 = 3000 万条“桶 → 设备序号”，每条 4 字节，加上容器开销 |
| CPU | 很低 | 心跳约 330 条/秒；查询平均 2–3 次/秒；信令峰值约 100 条/秒；单核足够 |
| 带宽：登记 | 约 80 MB/天 | 每台设备每天上传一次桶位图（8 KB，压缩前） |
| 带宽：转发对话 | 约 4–8 GB/天（约 120–240 GB/月） | 20 万次交换全部经信箱节点转发，每次约 20 KB，一个节点可能同时是双方的信箱节点 |
| 文件句柄 | 1 万+ | 把 `ulimit -n` 调到 65535 |

**结论：一台 1c1g 预计可以承载约 1–2 万台在线设备。** 瓶颈依次是：

1. 内存，取决于连接数；
2. 带宽：国内小水管（1–3 Mbps）走中继多的时候会紧张；
3. 重连风暴：节点重启时上万台设备同时重连并重新登记，需要客户端随机延迟 0–120 秒再重连，避免 TLS 握手瞬间压满 CPU。

### 3.2 水平扩展：节点之间不需要通信

| 机制 | 说明 |
|---|---|
| **桶归属** | 用加权的最高随机权重哈希（HRW / rendezvous hashing），根据节点列表算出每个桶归哪几个节点。副本数 R=2，任何一个节点宕机都不影响查询 |
| **一致性** | 所有小助手使用注册中心发布的**同一版**节点列表，算出的归属一致。节点之间**不需要同步任何数据** |
| **信箱节点** | 每台设备选 1 个节点作为信箱（可以是自建的），保持一条 WebSocket 长连接。**设备只和自己的信箱节点通信**，不连其他节点，也不连其他设备；信箱地址 = `节点 ID + 信箱 ID`，不含 IP |
| **登记** | 对每个桶索引节点，只发送**归它管的那部分桶**加上自己的信箱地址，用该索引节点的公钥加密后**经自己的信箱节点转发**（两跳，类似 Oblivious HTTP / RFC 9458）：信箱节点知道你的 IP 但看不到桶，索引节点看到桶但只知道信箱节点的 IP。信箱节点恰好也是某个桶的归属节点时，改经另一个节点转发。每台设备每天刷新一次，有效期 3 天 |
| **查询** | 新增内容所在的桶，同时向它的 2 个归属节点查询，结果合并；和登记一样两跳转发、加密 |
| **探测** | 查询方经自己的信箱节点，把探测消息转给对方的信箱节点，再由它通过长连接转给对方 |
| **对话** | 全程走“你 ⇄ 你的信箱节点 ⇄ 对方的信箱节点 ⇄ 对方”，**不直连、不打洞**。消息都是小文本（每次交换约 20 KB），走中继几乎没有成本；节点之间只转发密文，不同步任何数据 |
| **节点增减** | 节点列表变化后，小助手重新计算归属，只补登记被移走的桶（HRW 平均只移动 1/N）；旧节点上的记录过期后自动消失 |
| **信箱节点宕机** | 小助手换一个信箱节点并重新登记；指向旧信箱的记录探测失败后跳过 |

扩容方式就是**加节点**：节点越多，每个节点承担的桶越少，单个节点能看到的信息也越少（见 §5）。

### 3.3 费用策略

- **暂不接受捐赠。** 起步阶段用 Cloudflare 免费节点（免费版额度：Worker 每天 10 万次请求；Durable Objects 每天 10 万次请求、读 500 万行、写 10 万行；超额只报错不扣费）。这些额度足以支撑几百台设备试运行。
- Cloudflare 节点**超额时**会返回“过载”：小助手对这些桶改为使用副本节点；节点也在 `/.well-known/xseed` 中报告负载，注册中心的 CI 据此调低它的权重。
- 规模扩大后，靠社区节点承担；需要付费时再讨论。
- TURN 不使用（会计费），中继全部由节点自己承担。
- **站点侧成本**：优先用对方发来的种子，不访问站点；回退到从站点下载时，每次辅种下载 1 个种子，和手动下载一样，按站点限速（§9.7）。

## 4. 注册中心与节点准入

### 4.1 节点怎么加入

1. 运营者部署 `xseed-node`，生成节点密钥对；
2. 向 `xseed-registry` 提交 PR，新增 `nodes/<id>.yaml`，内容包括：地址、角色、地区、带宽和容量声明、节点公钥、联系方式；
3. CI 自动检查：
   - 访问 `/.well-known/xseed`，要求节点用私钥对挑战签名，证明地址确实由该密钥控制；
   - 检查协议版本、TLS 证书、延迟、可用性；
4. **仓库只有所有者可以推送**（分支保护），节点 PR 由所有者审核后合并；
5. 所有者在**本机**运行 `xseed-registry publish`：生成 `index.json`，用本机保存的私钥签名（minisign），然后推送。GitHub Actions 只负责把已签名的文件同步到 Releases、Pages、jsDelivr 等镜像，**不接触私钥**。

### 4.2 防滥用

| 风险 | 措施 |
|---|---|
| 一个人加很多节点，占住大部分桶（女巫攻击） | 每个运营者的总权重有上限；新节点从低权重开始，健康运行满 2 周才升到声明的容量 |
| 节点不稳定 | CI 每小时健康检查；连续 3 天不健康就自动提交下线 PR |
| 恶意节点丢弃登记、返回假信箱 | R=2 副本兜底；假信箱探测不通就跳过；小助手在本地给节点打分，表现差的降低优先级 |
| 镜像被篡改，或 GitHub 账号被盗 | 小助手只接受用所有者私钥签名、版本号递增的列表。私钥只在所有者本机，不在 GitHub 上，所以账号被盗也伪造不了签名。小助手内置一主一备两把公钥：备用私钥离线保存，主私钥丢失时用它签发新的主公钥。用户也可以固定使用自己的节点列表 |

### 4.3 小助手怎么选节点

- 每 6 小时拉取一次 `index.json`，验证签名后，保存最近一份有效的。
- 信箱节点和中继节点：在声明了相应角色的节点里挑延迟最低的，失败后换下一个。
- 桶索引节点：用 HRW 计算，不能自由选择（否则会找不到人）。

## 5. 信任

| 角色 | 能做的坏事 | 做不到的 | 应对 |
|---|---|---|---|
| **单个节点运营者** | 看到连接它的设备 IP；看到**归它管的那部分桶**（约 R/N 的比例）的登记和查询；拒绝服务。如果它自己也有某份文件，可以推断“某个 IP 可能有这份文件”（同一个桶里约十几份内容，无法确定是哪一份） | 读取任何对话内容；冒充任何一方；知道站点、种子 | 节点越多，单个节点看到的越少；R=2 副本；代码开源、构建可复现；用户可以只用自建节点 |
| **你的信箱节点** | 知道你的 IP、你在线、你和别人对话的时间与流量大小 | 读取对话内容；看到你登记了哪些桶（已用索引节点公钥加密）；知道你在和谁对话（只知道对方的信箱节点） | 用户可以自建信箱节点，这样你的 IP 只有你自己的节点知道 |
| **注册中心维护者** | 往列表里加入恶意节点 | 突破端到端加密 | 恶意节点能做的事情只限于第一行；用户可以固定自己的节点列表 |
| **对话对方** | 发送假的种子信息 | **拿到你的 IP**（对话全程经信箱节点转发）；拿到你在其他站的信息、你的 passkey；让你下载任何数据 | 拿到的种子要先核对 info_hash 和本机文件结构（§6.2），对不上就丢弃并在本地记差评 |
| **小助手软件本身** | 偷 passkey、误删种子 | — | 开源、可复现构建、签名发布、不静默自动更新；下载器操作白名单（§9.1） |

### 5.1 IP 隐藏：防止“拿到 IP 后绕过 tracker 直连下载”

社区反馈的攻击链：P2P 交换让别人拿到你的 IP → 探测出你的下载器端口 → 用种子的 info_hash 直接连上你的下载器下载，绕过 tracker。

**这条攻击链成立的前提**：BT 客户端会接受任何知道 info_hash 的对端连接，私有种子的 `private` 标记只关闭 DHT / PEX，并不拒绝陌生对端的主动连接。私有种子能挡住外人，靠的是“对端列表只有 tracker 给，而 tracker 只给会员”。因此，攻击者只要同时拥有 **①你的 IP 和下载器端口** 与 **②这个种子的 info_hash**，就能绕过 tracker。

- ②不能凭空算出：info_hash 需要完整的 info 字典，其中包括所有分块的 hash，只有拿到种子文件（站点会员，或者种子文件被泄露）才能得到。
- 但 ① 在 v0.5 中确实会泄露：v0.5 的探测只要求“知道结构指纹”，结构指纹可以从泄露的种子文件甚至公开的文件列表算出，而设备在通过锁 2、锁 3 **之前**就交换地址、尝试直连。所以“拿到泄露的种子 → 算出指纹 → 探测 → 拿到 IP → 直连下载”是一条可行的攻击链。**反馈成立。**

**v0.6 的修正：**

| 措施 | 效果 |
|---|---|
| 取消设备之间的直连，对话全程经双方的信箱节点转发 | 对话对方**永远拿不到你的 IP**，不管他有没有通过三道锁 |
| 登记和查询两跳转发，并按索引节点公钥加密 | 索引节点只知道“某个信箱登记了某个桶”，不知道 IP；信箱节点知道 IP，但不知道桶。要把 IP 和内容联系起来，需要**两个节点合谋** |
| 锁的顺序：锁 2、锁 3 全部通过之前，不发送任何种子信息 | 只有种子文件、没有数据或没有账号的人，什么都拿不到 |
| 可以自建信箱节点 | 你的 IP 只有你自己的节点知道 |

**仍然存在、不属于本系统的风险：** 你在某站做种时，该站 tracker 本来就会把你的 IP 和端口发给该种子的其他下载者，也就是所有能下载这个种子的会员。本系统不再额外泄露 IP。

## 6. 种子信息交换与加种

### 6.1 交换的内容：对方直接发种子，不行再从站点下载

种子文件里除了 info 字典，大多还带有站点自己的信息（comment、站点自定义字段等）。所以**不用 info 字典凭空拼一个种子**，而是由应答方把**它手里那份站点原版种子**去掉凭证后发过来，查询方只换上自己的 announce 地址，其余内容原样保留。

应答方发送：`{ 去掉凭证的 .torrent, tracker 主机列表, info_hash（v1 / v2）, 种子编号, 详情页地址 }`。

**去掉凭证（必须做到，有单元测试覆盖）：**

| 部分 | 处理 | 原因 |
|---|---|---|
| `info` 字典 | 原样保留，不能改 | info_hash 由它算出；它对所有用户都一样，不含个人信息 |
| `announce` / `announce-list` | 每个地址只保留 `scheme://host[:port]`，**保留分层结构** | passkey 就在路径或查询串里 |
| 其他顶层字段 | 按**白名单**保留：`creation date`、`created by`、`encoding`、`comment`；comment 中的链接按下面详情页地址的规则清洗 | 有的站点会在种子里写入用户名、用户 ID 等“水印”，不在白名单中的字段一律删除，避免泄露应答方身份 |
| `url-list` 等 | 删除 | 可能带凭证 |
| 详情页地址 | 只保留 `scheme://host/path`，加上白名单中的编号参数（`id`、`torrentid`、`tid`） | 去掉其余查询参数 |

**查询方获取可用种子**（按顺序尝试；哪种方式对哪个 tracker 有效，按 §8.5 记住）：

1. **用对方发来的种子**：把每个 tracker 主机替换成本机该 tracker 已有种子的 announce 地址（带自己的 passkey，分层结构按主机名对应）。本机没有这个 tracker 的种子，拿不到 announce 地址时，跳到第 2 步。
   - **事先判断（不发任何请求）**：如果本机该 tracker 下各个种子的 announce 地址除了 passkey 之外还有差别，说明带了按种子生成的密钥，直接跳到第 2 步。
   - 加入后 tracker 返回认证失败或“未注册”：删除种子（不删文件），跳到第 2 步。
2. **从站点下载**：用自己的账号按下载地址下载。下载地址的来源：
   - 站点定义里的模板，导入 PT-depiler 时按站点框架（NexusPHP / Gazelle / UNIT3D 等）自动生成；
   - 没有站点定义的，用详情页地址的域名按通用地址去试，例如 NexusPHP 的 `download.php?id={id}&passkey={passkey}`。
3. **都不行**（需要 Cookie 或 API 令牌但用户没有配置，或者地址格式推导不出来）：放弃这一条，并在 Web UI 中提示用户为该站配置凭证。

### 6.2 查询方收到信息后的处理

```
1. 按 §6.1 得到种子（对方发来的，或从站点下载的）
   - 种子的 info_hash 必须等于对方声明的            → 不一致：丢弃，对方记差评
   - 结构指纹必须等于本机的                         → 不一致：丢弃，对方记差评（不读盘）
2. 判断内容是否已被证明一致：
   - pieces 的 SHA-1 与本机种子相同，或 v2 每个文件的根相同 → 0 读盘，直接进入第 3 步
   - 只有结构一致（piece 大小不同）                     → 抽查（§7.2），少量读盘
4. 加入下载器：skip_checking=true、autoTMM=false、显式指定保存路径、打上 xseed 标签
5. 观察下载器状态：
   - 出现 missingFiles / error                  → 删除种子（不删文件）
   - tracker 返回 “unregistered / not registered” → 删除种子（不删文件），并把这条映射记为失效
   - 正常                                       → 随机延迟 0–10 分钟后开始做种
```

### 6.3 信任本机下载器状态

按你的决定，**不做全量 hash 校验**，以本机 qB / TR 的状态为准。具体条件如下：

| 条件 | 怎么判断 | 读盘 |
|---|---|---|
| 本机原种子已完成 | 进度 == 1.0，状态是做种 / 暂停做种 / 排队做种之一，不是 checking、missingFiles、error | 0 |
| 文件还在原位、大小没变 | 对每个文件 `stat`，大小一致 | 0（只读元数据） |
| 新种子的基础检查 | 交给下载器：qB 用 `skip_checking` 加入后，libtorrent 仍会检查文件是否存在、大小是否一致，不对就进入 error 状态 | 0 |
| Transmission | TR 的 RPC 没有“跳过校验”参数（实现时核实），加入后如果它自己做校验，也属于下载器自身的检查，我们接受 | 由 TR 决定 |

**站点规则：** 站点定义中标记 `allow_skip_check: false` 的站点（明令禁止跳过校验），对这个站点的种子改为正常校验，进入按盘排队的校验队列（§7.3）。

## 7. 硬盘损耗

### 7.1 读盘量

| 环节 | 读盘量 |
|---|---|
| 指纹计算、结构比对、状态判断 | **0**（全部来自下载器 API 和 `stat`） |
| 锁 2 现场抽查（应答和提问） | 每次对话 3 段 × 16 KB |
| 内容已被证明一致时加种 | **0** |
| 只有结构一致时的抽查 | 见 7.2，通常为几 MB 到几十 MB |
| 全量校验 | **不做**（禁止跳过校验的站点除外） |

### 7.2 只有结构一致时的抽查

piece 大小不同时，没有 hash 能直接证明内容相同。最常见的“结构相同、内容不同”是**音乐文件改标签**和**修改 nfo / 字幕**，而改动集中在文件的**开头和结尾**（FLAC / ID3v2 标签在开头，ID3v1 / APE 标签在结尾）。所以：

- 校验新种子中**覆盖每个文件开头和结尾的 piece**，再加 2 个随机 piece；
- 总数最多 32 个 piece，超过时优先校验小文件；
- 只要有一个不一致，就放弃。

### 7.3 其他

- **休眠的机械硬盘**：抽查读盘量很小，但仍可能唤醒硬盘。可选配置“工作时间窗”（默认关闭）：时间窗外延迟应答，并批量处理抽查。
- **禁止跳过校验的站点**：按盘排队，每块盘同时只校验 1 个种子，每天读取预算 500 GB。
- **只用硬链接，绝不复制数据**：目录结构完全一样时直接复用原保存路径；否则在同一文件系统内建硬链接（支持的话用 reflink）；跨文件系统时跳过。

## 8. 站点定义库

### 8.1 来源与维护

| 阶段 | 做法 |
|---|---|
| 第一版 | 写一个导入脚本，从 [PT-depiler](https://github.com/pt-plugins/PT-depiler)（MIT 协议，约 415 个站点定义）导入站点 ID、名称、网址（含历史网址）、站点框架类型。PT-depiler **没有记录 tracker 的 announce 域名**，所以 tracker 主机按以下方式补全：①默认把站点域名及其子域名（如 `tracker.xxx`）视为该站的 tracker；②社区通过 PR 补充独立的 tracker 域名或 IP |
| 之后 | 在 `xseed-registry/sites/` 中维护，**只有所有者可以推送**（其他人可以提 Issue 或 PR，由所有者合并）；在 README 中保留 PT-depiler 的 MIT 版权声明 |
| 分发 | 和节点列表一起打包进签名的 `index.json`，小助手每 6 小时拉取一次。jsDelivr 镜像方便国内访问 |
| 隐私 | 沿用 PT-depiler 的做法，网址和域名用 ROT13 编码存放，避免被搜索引擎直接收录 |

`sites/<id>.yaml` 的字段：`id, name, urls[], tracker_hosts[]`（域名或 IP，可以带端口）、`schema`（站点框架，用于推导下载模板），以及可选的 `allow_skip_check`（默认 true）、`p2p`（allow / deny）。种子来源、下载地址和 scrape 支持**不需要人工填写**，由小助手自动学习（§8.5）。

### 8.2 识别种子属于哪个站

- 一个种子可能有**多个 tracker**（多个分层，或者同一层里有多个地址）：把每个 tracker 地址的主机名小写化，与所有站点的 `tracker_hosts` 匹配，结果取并集。
- 匹配到 **1 个站点**：这个种子属于该站。
- 匹配到**多个站点**（共用 tracker 的姊妹站，或者被人手工加了 tracker）：标记为“归属不明”，不登记也不查询，在 Web UI 中提示。
- 只匹配到公共 tracker（DHT、公网 tracker 列表）：忽略这些地址，只看剩下的。

### 8.3 没有站点定义的 tracker

按你的要求，**只要 tracker 域名对得上就可以**：

- 站点身份直接用 tracker 主机名表示（`host:<小写主机名>`）。
- 交换时比较双方 tracker 主机名的交集。有交集，就说明双方在同一个 tracker 有账号。
- 多 tracker 的情况：只要有一个主机名相同就算匹配。
- 优先用对方发来的种子（§6.1 第 1 步），只需要本机有该 tracker 的 announce 地址；需要回退时按通用地址试，试通了就记住。
- 有多个这样的主机名在同一个站点上（站点换过域名），等该站有了站点定义后自动合并。

### 8.4 会员验证（锁 3）的三种方式

| 方式 | 适用于 | 做法 | 强度 |
|---|---|---|---|
| 会员钥匙 | 配合的站点（PT Studio） | 种子信息用站点每周发放的钥匙加密 | 强 |
| **scrape 挑战**（新增） | 所有支持带 passkey scrape 的 tracker，**包括没有站点定义的** | 应答方从自己在该 tracker 的其他种子里随机挑一个 info_hash，查询方用**自己的** passkey 去 scrape，报出 `downloaded`（完成数）；应答方自己也 scrape 一次，两边差值在 ±2 以内才通过。不需要下载种子，也不会在 tracker 上留下 peer 记录 | 中等：能证明对方此刻持有该 tracker 的有效 passkey |
| 下载挑战 | 站点定义中配置了下载地址、且 tracker 不支持 scrape 的站点 | 同 v0.1 | 中等 |

**回退顺序**（不依赖人工标记，结果按 §8.5 记住）：会员钥匙（站点提供时）→ scrape 挑战 → 下载挑战（需要站点定义中有下载模板）→ 都不行时默认不交换，用户可以针对单个 tracker 开启“宽松模式”，只要求锁 1 和锁 2。

scrape 挑战失败的判定：HTTP 错误、返回 “not supported” 一类的失败原因、`files` 为空，或者连续 3 次两边结果对不上。判定为失败后，这个 tracker 本地记为“不支持 scrape”，30 天内不再尝试。

### 8.5 站点特性的自动学习与发布

| 项 | 说明 |
|---|---|
| 学什么 | 每个 tracker 主机的 `torrent_source`（peer：对方发来的种子可用 / site：必须从站点下载）、`download`（可用的下载地址模板）、`scrape`（ok / unsupported），以及证据（发生时间、错误类型，**不含任何凭证或种子信息**） |
| 存在哪 | 小助手本地数据库的 `host_traits` 表 |
| 优先级 | 本机学到的结果 > 注册中心发布的结果 > 默认值（peer、按站点框架推导的模板、scrape ok）。本机结果 30 天后过期重试，以免站点调整后一直用旧结论 |
| 怎么汇总到 GitHub | 任何人都可以在 Web UI 或命令行运行 `xseed-agent traits export`，导出一段 YAML 贴到 Issue 里；**只有所有者**把它合并进 `xseed-registry/traits/`，在本机签名后推送 |
| 客户端怎么用 | 跟节点列表、站点定义一起，每 6 小时从 GitHub 拉取（验证签名），作为新装客户端的初始值，减少每台设备各自试错一次 |
| 隐私 | 小助手**不会自动上传**学到的结果，导出必须由用户手动触发 |

## 9. 其他实际因素

### 9.1 下载器安全

| 规则 | 原因 |
|---|---|
| `autoTMM=false`，显式指定保存路径 | 防止 qB 的自动管理移动文件 |
| 删除种子时**永远**带 `deleteFiles=false` | 数据属于原种子 |
| 只操作带 `xseed` 标签、并且本地数据库有记录的种子 | 不碰用户的其他种子 |
| 加入前检查 info_hash 是否已存在 | 和 IYUU、cross-seed 共存 |
| 全部操作幂等，可以中断恢复 | 小助手重启后继续 |
| 首次运行默认试运行模式 | 先只列出“会辅种什么”，让用户确认 |

### 9.2 路径映射（Docker）

配置 `path_map`，启动时抽样检查：用下载器报告的路径在本地 `stat`，大小对得上才算配置正确。

### 9.3 Tracker 与反作弊

- 加种后随机延迟 0–10 分钟再启动，错开 announce。
- PT Studio 的 anticheat 规则集要加入“第一次 announce 就是做种状态”的回测样例。

### 9.4 网络环境

设备只需要一条连到自己信箱节点的出站 WebSocket over TLS（443 端口），**不打洞、不监听端口**，任何 NAT 或防火墙环境都能使用；支持 HTTP / SOCKS5 代理。

### 9.5 冷启动与只查不答

对称交换：新持有者查询时，老持有者也顺带拿到新映射，所以只需查询新增内容。关闭应答的用户，每天的查询次数减半。

### 9.6 本地安全与资源

- 凭证加密存储，日志脱敏，Web UI 默认只监听 127.0.0.1。
- 资源目标：空闲时内存 < 60 MB；ARM NAS 可以运行。

### 9.7 时钟、限流、多设备、合规

- 会员钥匙接受本周和上周两把；本地时钟偏差超过 5 分钟时告警。
- 限流：
  - 节点按 IP 限制新信箱数，新信箱需要约 1 秒的工作量证明；
  - 节点按信箱限制每分钟收到的探测数；
  - 应答方按天限制应答次数；
  - 站点种子下载：每个站点每分钟 2 个、每天 200 个，加随机间隔，可以按站点覆盖；
  - scrape 挑战和下载挑战，每个站点每天各 20 次。
- 同一套下载器只运行一个小助手。
- 系统不传输影音文件数据；尊重站点的 `deny` 声明；Cloudflare 节点上线前，逐条核对 Cloudflare 的服务条款。
